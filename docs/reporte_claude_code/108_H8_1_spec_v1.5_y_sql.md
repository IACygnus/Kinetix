## 1. Lo que el diagnóstico encontró antes de escribir nada

Cuatro cosas, y tres cambiaron el plan.

### 1.1 No existe `is_closed`

H-D80 hablaba de «columna nueva» y H-D81 de «el campo `is_closed` que ya
existe». Ninguno de los dos describía la base. Lo que hay es:

```
status | character varying(20) | not null | (sin DEFAULT en la base)
CHECK (status IN ('activo','cerrado'))
closed_at, closed_by
ix_projects_status
```

Se usa en **20 sitios del backend** y **8 del frontend**. Y el `DEFAULT` no está
en la base: lo pone SQLAlchemy desde el modelo, así que el SQL no tiene que
tocarlo.

El estado de la base el día del diagnóstico: **10 proyectos, los 10 `activo`**,
**ningún `cerrado`**, 24 registros de horas entre el 1 y el 17 de septiembre. La
migración de H-D81 no mueve ni una fila hoy; el `UPDATE` de `cerrado` está de
todos modos, porque la base del servidor puede no estar igual.

**Decisión de Fredy:** reusar `status` y ampliar el CHECK. «Dos columnas que
significan lo mismo acaban con alguien leyendo la equivocada.»

### 1.2 El truco de O-D33 no aplica aquí, y no hace falta

H-D87 pedía copiar O-D33: no declarar la columna en el modelo hasta que Fredy
aplicara el SQL. Eso protege contra una columna **nueva** que SQLAlchemy pediría
en cada `SELECT` y que aún no existe —fue lo que reventó la pantalla de
monitoreo en la Etapa 2 con `ai_config.reasoning_effort`—.

`status` no es nueva: está declarada desde H1 y **leerla nunca falla**, ni antes
ni después del SQL. Lo único que puede fallar es **escribir** un valor que el
CHECK todavía no acepte. Por eso la protección es otra, y está en el propio SQL
(§2).

### 1.3 El consumo tenía que renombrarse, y la clave interna ya lo decía

H-D82 cambia «En ejecución» por «En rango» en la columna de Consumo. No es un
capricho: `en_ejecucion` es ahora un **estado** del proyecto, y dos cosas
distintas no pueden llamarse igual en la misma fila.

Lo notable es que **la clave interna de `desfase.py` ya se llama `en_rango`**
desde H2b; v1.3 le puso el rótulo «En ejecución» solo para pantalla. H-D82
devuelve el texto a su clave, así que el cambio en el backend es de una línea del
diccionario `TEXTOS`, no de la lógica.

Lo que sí se retira de verdad es el quinto valor del consumo:

- `desfase.CERRADO` y el parámetro `cerrado: bool` de `estado()` y `etiqueta()`
  quedan sin uso — los llaman `time_projects.py` (4 sitios) y
  `time_consulta.py` (2);
- el tipo `OverrunStatus` de `horasApi.ts` pierde `'cerrado'`, y con él las dos
  ramas de `AvisoDesfase.tsx` que lo pintaban en gris.

Todo eso es de H8.2 y H8.3. Aquí solo queda escrito.

## 2. El SQL — `docs/sql/h8_estado_proyecto.sql`

**Escrito, no ejecutado.**

Hace tres cosas: borra el CHECK viejo, pone uno nuevo, y migra las filas. Va
entero dentro de una transacción, y al terminar imprime el recuento por estado
—la comprobación, no la suposición—.

### Por qué el CHECK acepta **siete** valores y no cinco

Es la parte que sustituye a la protección de O-D33. El SQL y el código de H8.2
se despliegan por separado, y el orden no puede importar:

| Si pasa esto… | …con un CHECK de cinco |
|---|---|
| Se aplica el SQL y sigue corriendo el código viejo | El código viejo escribe `'activo'` al crear un proyecto → **error de base de datos** |
| Se despliega el código nuevo sin haber aplicado el SQL | El código nuevo escribe `'en_ejecucion'` → **error de base de datos** |

Aceptando los siete —los cinco nuevos más `activo` y `cerrado`—, las dos mitades
funcionan durante el intervalo, se aplique lo que se aplique primero. **En H8.6,
con el código nuevo ya vivo, un segundo script lo estrecha a cinco.**

### Idempotencia

`DROP CONSTRAINT IF EXISTS` seguido de `ADD`: se puede ejecutar las veces que
haga falta, esté la restricción o no, se haya cambiado antes o no. Los dos
`UPDATE` solo tocan filas que sigan en los valores viejos, así que una segunda
ejecución no mueve nada.

### El historial no necesita SQL

`project_status_changes` —el historial de H-D83— es una **tabla nueva**, y las
tablas nuevas las crea `Base.metadata.create_all` al arrancar (regla 10). No hay
nada que ejecutar para ella. Por eso el SQL de esta etapa es una sola columna, y
no una migración.

### La tabla que decide todo lo demás (§3.1)

| Estado | Registrar horas | Cambiar estimaciones |
|---|---|---|
| Pendiente | No | Sí |
| En ejecución | **Sí** | Sí |
| Detenido | No | Sí |
| No viable | No | No |
| Finalizado | No | No |

Pendiente y detenido son temporales: **se planifican aunque no se registren**, y
por eso admiten cambios de estimación. No viable y finalizado están cerrados a
todo.

**La excepción de la importación** (§6.2.8) merece decirse aparte: un Excel trae
horas de hace semanas y el proyecto pudo cambiar de estado desde entonces.
Rechazarlas obligaría a reabrir el proyecto, importar y volver a cerrarlo. Así
que la importación entra en cualquier estado **salvo `no_viable`**, y la vista
previa avisa de cuántas filas caen en proyectos que no están en ejecución.
